# Complete System Test Guide

Manual end-to-end test of the master chart (`helm/salt-master`), the key
operator (`helm/salt-key-operator`, installed as a subchart of the master
chart) and the minion chart (`helm/salt-minion`) on a real cluster.

The commands were checked against the current chart templates (names, values,
labels, `helm template` output). They have not all been run end to end on a
cluster for this revision; master cluster mode (scenario 6) was run on a real
cluster with three replicas and isolated storage, without the minion steps. If a step fails, trust the chart templates over this text and fix the
document.

There is no Helm chart for `salt-minion-vcf`. To test the VCF image, install the
`salt-minion` chart with that image (scenario 7).

## Prerequisites

- Kubernetes 1.24+ cluster, `kubectl` and `helm` (v3) configured, about 4 CPU and
  8 GiB free, and a default StorageClass (cluster mode and `jobCache` need PVCs).
- Docker, if you build images yourself (see [`building.md`](building.md)).
- Images the nodes can pull. Chart defaults: master `salt-master:3008.5`
  (unqualified, so build and import it, or override it), minion
  `ghcr.io/saltstack/salt-kubernetes/salt-minion:0.1.0`, operator
  `ghcr.io/saltstack/salt-kubernetes/salt-key-operator:0.1.0`. Override them with
  `agent.image.repository`/`agent.image.tag` (master, minion) and
  `salt-key-operator.image.repository`/`salt-key-operator.image.tag` (the operator,
  set on the master release). A private registry needs
  `<registry>/<project>/<image>`; see [`helm-test.md`](helm-test.md).

```bash
docker build -t salt-master:3008.5 src/master
docker build -t salt-minion:0.1.0 src/minion/kubernetes
docker build -t salt-key-operator:0.1.0 src/salt-key-operator
helm dependency update helm/salt-master
```

Names used below: the master release is `salt-master` in namespace `salt-master`,
the minion release is `salt-minion` in namespace `salt`. The master StatefulSet
is always named `salt-master` (pods `salt-master-0`, ...), container `salt-master`.
The minion StatefulSet is named `agent.minion.idPrefix`, default `salt-minion`
(pods `salt-minion-0`, ...).

```bash
M="kubectl -n salt-master exec salt-master-0 -c salt-master --"
```

## Scenario 1: Single master, manual key acceptance

Disables the operator so `salt-key -a` works.

```bash
helm lint helm/salt-master helm/salt-minion helm/salt-key-operator
helm upgrade --install salt-master helm/salt-master \
  --namespace salt-master --create-namespace \
  --set agent.trustedMinions.enabled=false \
  --wait --timeout 5m
kubectl -n salt-master get pods -l app=salt-master
$M salt-key -L
$M salt-run test.arg testing
```

Expected: pod `salt-master-0` is `Running` and ready, `salt-key -L` lists no
keys, ports 4505 and 4506 listen. There are no Kubernetes probes on the master
pod; "ready" only means the container started.

Master key (chart-generated by the `salt-master-master-keygen` Job into Secret
`salt-master-master-keys`, keys `master.pem` and `master.pub`):

```bash
kubectl -n salt-master get secret salt-master-master-keys \
  -o jsonpath='{.data.master\.pub}' | base64 -d | sha256sum
$M cat /etc/salt/pki/master/master.pub | sha256sum
```

Expected: identical hashes.

## Scenario 2: One minion

```bash
helm upgrade --install salt-minion helm/salt-minion \
  --namespace salt --create-namespace \
  --set agent.saltMasterHost=salt-master.salt-master.svc.cluster.local \
  --set agent.minion.allowSelfGeneratedKey=true \
  --wait --timeout 5m
kubectl -n salt get pods -l app=salt-minion
kubectl -n salt get secret salt-minion-keys   # minion.pem, minion.pub from the keygen Job
```

The minion ID is the pod name (`salt-minion-0`). The minion pod has liveness and
readiness probes (`salt-call --local test.ping`).

```bash
$M salt-key -L                       # salt-minion-0 is pending
$M salt-key -a salt-minion-0 -y
$M salt salt-minion-0 test.ping      # True
kubectl -n salt exec salt-minion-0 -- salt-call --local test.ping
```

The chart sets `agent.minion.allowSelfGeneratedKey=true` only to avoid supplying
keys; other key sources (`agent.minion.keySecretName`, inline keys) are in the
[minion chart README](../helm/salt-minion/README.md).

## Scenario 3: Several minions, one keypair each

Each replica is a separate minion with its own ID and keypair. Replace the single
minion (a release cannot change layout cleanly, and the old Secret holds a single
`minion.pem`/`minion.pub` pair):

```bash
helm uninstall salt-minion -n salt
kubectl -n salt delete secret salt-minion-keys
helm upgrade --install salt-minion helm/salt-minion \
  --namespace salt \
  --set agent.saltMasterHost=salt-master.salt-master.svc.cluster.local \
  --set agent.minion.allowSelfGeneratedKey=true \
  --set agent.replicas=3 \
  --wait --timeout 5m
kubectl -n salt get pods -l app=salt-minion
kubectl -n salt get secret salt-minion-keys -o json | jq -r '.data | keys[]'
for i in 0 1 2; do
  kubectl -n salt exec salt-minion-$i -- sha256sum /etc/salt/pki/minion/minion.pub
done
```

Expected: pods `salt-minion-0..2`; the Secret has `salt-minion-N.pem` and
`salt-minion-N.pub` for each pod, and the keygen Job is named
`salt-minion-keygen-3`; the three hashes differ (each pod mounts only its own
pair). `kubectl -n salt exec salt-minion-1 -- salt-call --local grains.get id`
returns `salt-minion-1`. Scaling up later only adds the missing pairs; scaling
down leaves the extra pairs in the Secret.

The chart rejects `agent.minion.id`, and inline `privateKeyB64`/`publicKeyB64`,
when `agent.replicas > 1` (checked with `helm template`).

Accept all three minions and ping them:

```bash
for i in 0 1 2; do $M salt-key -a salt-minion-$i -y; done
$M salt '*' test.ping
```

## Scenario 4: Key operator (declarative acceptance)

With `agent.trustedMinions.enabled=true` (the default) the master chart installs
the operator in the release namespace and runs a `trusted-minions-sync` sidecar in
every master pod. The sidecar copies the ConfigMap `salt-master-trusted-minions`
into Salt's key directory and **removes keys that are not in the ConfigMap**, so
`salt-key -a` no longer sticks. Do not install `helm/salt-key-operator` separately
into the same namespace as well: it would clash with the subchart.

```bash
for i in 0 1 2; do $M salt-key -d salt-minion-$i -y; done   # remove manual acceptance
helm upgrade salt-master helm/salt-master \
  --namespace salt-master \
  --set agent.trustedMinions.enabled=true \
  --wait --timeout 5m
kubectl -n salt-master get pods -l app=salt-key-operator
kubectl -n salt-master logs deploy/salt-key-operator --tail 50
```

Create one `SaltMinionKey` per minion pod from its public key:

```bash
for i in 0 1 2; do
  PUB=$(kubectl -n salt get secret salt-minion-keys \
    -o jsonpath="{.data.salt-minion-$i\.pub}" | base64 -d)
  kubectl apply -f - <<EOF
apiVersion: salt.saltstack.io/v1alpha1
kind: SaltMinionKey
metadata:
  name: salt-minion-$i
  namespace: salt-master
spec:
  minionId: salt-minion-$i
  publicKey: |
$(echo "$PUB" | sed 's/^/    /')
EOF
done
kubectl -n salt-master get saltminionkey
kubectl -n salt-master get configmap salt-master-trusted-minions -o jsonpath='{.data}' | head -c 300
```

Wait up to two minutes (kubelet ConfigMap resync plus the sidecar's
`syncIntervalSeconds`, default 15 s), then:

```bash
$M salt-key -L            # salt-minion-0..2 accepted
$M salt '*' test.ping
```

Delete one and confirm it disappears from `salt-key -L` after the same delay:

```bash
kubectl -n salt-master delete saltminionkey salt-minion-2
```

The `SaltMinionKey` must be in the same namespace as the master release (the
operator finds the ConfigMap labelled `salt.saltstack.io/trusted-minions=true` in
its own namespace).

## Scenario 5: Classic multi-master

All replicas share one keypair that you supply. Start from a clean master:

```bash
helm uninstall salt-master -n salt-master
kubectl -n salt-master delete secret salt-master-master-keys --ignore-not-found
kubectl -n salt-master delete pvc --all

openssl genrsa -out /tmp/master.pem 2048
openssl rsa -in /tmp/master.pem -pubout -out /tmp/master.pub
kubectl -n salt-master create secret generic salt-master-keypair \
  --from-file=master.pem=/tmp/master.pem --from-file=master.pub=/tmp/master.pub

helm upgrade --install salt-master helm/salt-master \
  --namespace salt-master \
  --set agent.replicas=3 \
  --set agent.masterKeySecretName=salt-master-keypair \
  --wait --timeout 5m

for i in 0 1 2; do
  kubectl -n salt-master exec salt-master-$i -c salt-master -- \
    sha256sum /etc/salt/pki/master/master.pub
done
```

Expected: three identical hashes. Without `agent.masterKeySecretName` and with
`agent.replicas=3`, `helm template` fails by design.

Point minions at every master through the headless Service (each is an
independent connection; this is not failover):

```bash
helm upgrade salt-minion helm/salt-minion --namespace salt --reuse-values \
  --set 'agent.saltMasterHost={salt-master-0.salt-master-headless.salt-master.svc.cluster.local,salt-master-1.salt-master-headless.salt-master.svc.cluster.local,salt-master-2.salt-master-headless.salt-master.svc.cluster.local}'
```

Create the `SaltMinionKey` objects as in scenario 4 (the operator subchart is
installed again with the master), then check every master sees the keys:

```bash
for i in 0 1 2; do
  kubectl -n salt-master exec salt-master-$i -c salt-master -- salt-key -L
done
```

Expected: the minion keys are accepted on all three masters.

## Scenario 6: Master cluster mode

Needs `agent.replicas >= 2` (use 3) and a default StorageClass (one PVC per pod).
Start from a clean master as in scenario 5, then:

```bash
helm upgrade --install salt-master helm/salt-master \
  --namespace salt-master \
  --set agent.cluster.enabled=true \
  --set agent.replicas=3 \
  --wait --timeout 10m
kubectl -n salt-master get pods -l app=salt-master
kubectl -n salt-master get secret salt-master-cluster-secret
kubectl -n salt-master exec salt-master-0 -c salt-master -- salt-run cluster.members
```

Expected: three ready pods and three cluster members. Minions use the flat
Service and any replica serves any minion:

```bash
helm upgrade salt-minion helm/salt-minion --namespace salt --reuse-values \
  --set agent.saltMasterHost=salt-master.salt-master.svc.cluster.local
```

Accept the minions with `SaltMinionKey` objects (as in scenario 4; in cluster mode
the keys are written into the cluster PKI directory). Not covered by this
revision: shared storage mode, minions through the cluster, node failure.

**Do not delete or restart a master pod in this scenario.** The pod IP is the
cluster identity and changes on restart; a restarted master cannot rejoin and
quorum is lost after the second restart. See "Master cluster" in the
[master chart README](../helm/salt-master/README.md).

## Scenario 7: VCF minion image

The VCF image (`src/minion/vcf`, `salt-minion-vcf`) is used through the same minion
chart. Untested here:

```bash
helm upgrade --install salt-minion helm/salt-minion --namespace salt \
  --set agent.saltMasterHost=salt-master.salt-master.svc.cluster.local \
  --set agent.minion.allowSelfGeneratedKey=true \
  --set agent.image.repository=<your-registry>/<project>/salt-minion-vcf \
  --set agent.image.tag=0.1.0
kubectl -n salt exec salt-minion-0 -- salt-call --local grains.get id
```

## Cleanup

```bash
helm uninstall salt-minion -n salt
helm uninstall salt-master -n salt-master
kubectl -n salt delete secret salt-minion-keys --ignore-not-found
kubectl -n salt-master delete secret salt-master-master-keys salt-master-keypair --ignore-not-found
kubectl -n salt-master delete pvc --all
kubectl delete namespace salt salt-master
```

Chart-generated Secrets (master keys, cluster secret, minion keys), the
`SaltMinionKey` CRD and PVCs are not removed by `helm uninstall`. Delete them to
start with a new identity.

## Success criteria

- `helm lint` passes for the three charts.
- Master pods start; `salt-key -L` and `salt` commands work.
- Minions appear (pending, then accepted) and answer `test.ping`; with several
  replicas each pod has a distinct ID and keypair.
- Operator: `SaltMinionKey` creates and deletes accepted keys on every master
  replica.
- Classic multi-master: identical `master.pub` on all replicas.
- Cluster mode: `cluster.members` lists every master.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Pod `Pending` | `kubectl describe pod`; PVC binding, node selector, resources. |
| `ImagePullBackOff` | Image path, registry trust on nodes, `pullPolicy`; see `helm-test.md`. |
| Minion does not connect | `kubectl -n salt logs salt-minion-0`; `kubectl -n salt exec salt-minion-0 -- nc -zv salt-master.salt-master.svc.cluster.local 4506`. |
| Minion pod stuck in init | The key Secret is missing: `kubectl -n salt get job,secret`; check the keygen Job logs. |
| Key not accepted on master | `kubectl -n salt-master get configmap salt-master-trusted-minions -o yaml`; `kubectl -n salt-master logs salt-master-0 -c trusted-minions-sync`; operator logs. |
| `salt-key -a` key vanishes | The operator sidecar removes keys that are not in the ConfigMap (scenario 4). |
| Master install fails on `agent.replicas` | Classic multi-master needs `agent.masterKeySecretName`; cluster mode needs `agent.replicas >= 2`. |
